# Wiki tooling in `ai`

Status: draft · Project 1 of 3 (2: spec-driven workflow preset, 3: task MCP)

## Intent

The user wants spec-driven development with memory that lasts. That memory has three layers:

| Layer | Holds | Lifetime |
|---|---|---|
| Wiki (`docs/wiki/`) | what the system is now | updated in every change |
| Spec (`docs/specs/`) | intent, why, approaches, the option picked | frozen after merge |
| Commit | code, wiki update, a `Spec:` trailer | permanent |

This project covers the wiki layer. gym-rice has a working wiki: pages with a `covers:` frontmatter, a generated `docs/index/`, a `scripts/wiki.mjs` for `index`/`check`/`affected`, and a Claude Stop hook that nudges for wiki updates. All of it is local to gym-rice. The goal is to make it one general tool that any repo can opt into through `harness.json`, so agents starting a task and the user, months later, both find the current truth the same way in every repo.

## Goals

- Any repo turns on the wiki with a `wiki` section in `harness.json`, and `air apply` sets it up.
- One source of the tooling, in this repo, and a self-contained wiki in every project.
- The "update the wiki" nudge works on Claude (local and cloud) and on pi.
- gym-rice moves onto the general tooling with no change in behavior.

## Non-goals

- The spec layer, the superpowers preset, and the close-the-change step. Those are project 2. This project only makes `check` leave `docs/specs/` alone.
- Changing gym-rice's wiki conventions or content.
- A UI or a search tool over the wiki.

## Anti-goals

- A spec that can make a machine run code from outside this repo. `harness.json` stays data only.
- A global hook that runs code from whatever repo it happens to be in.
- A hook that fires twice, or nags after the agent has already answered "no update needed".

## Decisions (the user's)

1. **Config in `harness.json`.** A new optional `wiki` key, data only. It holds at least the source directories the index mirrors (gym-rice: `["app", "worker"]`). `wiki.mjs` reads its config from the project's `harness.json`.
2. **Hook installed per repo by `air apply`, wherever that's possible.**
   - Claude: `apply` adds a Stop hook to `.claude/settings.local.json` (already git-excluded).
   - Pi: a `wiki` extension that `apply` adds to the project's `.pi/settings.json` (see the opt-in extension call below).
3. **Global fallback** for where `apply` doesn't run (Claude cloud sessions): the global `ai` plugin carries the same Stop hook. It does nothing unless the repo has `docs/wiki/`, and nothing in a repo where `apply` already installed the repo-level hook.
4. **`wiki.mjs` written into each project.** `apply` writes `scripts/wiki.mjs` into the project as a committed file with a "generated by air" header, and refreshes it on every `apply`. The project's pre-commit (`npm run wiki:check`) then works in any clone, with or without `air`. Updates show up as diffs the user reviews and commits, like `docs/index/`.

## Approaches considered

- **Hook delivery:** global only, per-repo only, or conventions with no hook. Picked: per repo where possible, global as the fallback.
- **Where `wiki.mjs` lives:** only in `ai` (pre-commit calls `air wiki check`; every clone needs `air`), generated and committed into each project, or hand-maintained per project (copies drift). Picked: generated and committed.

## Calls made in design (the builder may revisit; flag if wrong)

- **Source layout.** An opt-in skill `skills/wiki/` holds `SKILL.md`, `scripts/wiki.mjs`, `scripts/wiki-stop-hook.mjs`, and a `docs/README.md` template. The skill text tells an agent how to work with the wiki, and how to bootstrap one from existing code in a repo that has none, as was done for gym-rice.
- **Conventions authority.** Each project's `docs/README.md` stays the authority on its conventions, so the repo explains itself without `air`. The skill's template is only the starting point for new repos.
- **Hooks run `ai`'s copy, never the project's.** Both the repo-level hook and the global fallback run `wiki-stop-hook.mjs` from the `ai` clone, which imports the `ai` copy of `wiki.mjs`. Otherwise a global hook would execute any cloned repo's `scripts/` on Stop.
- **Specs exempt.** `check` skips `docs/specs/`. Specs are dated and historical, which the wiki's style rules ban.
- **Generalized, not rewritten.** `wiki.mjs` keeps gym-rice's behavior. Only the hardcoded values (`SOURCE_DIRS`, and any topic or path assumptions found while porting) move into the config.
- **Generated file ownership.** `apply` overwrites `scripts/wiki.mjs` only if it carries the "generated by air" header or `apply` wrote it before. Otherwise it fails, as `syncCopiedSkills` does for skill copies. gym-rice's migration replaces its hand-written copy once, with the user's OK.
- **Repo-hook marker.** The global fallback recognizes a repo-level install from `air`'s own state, or from the hook entry in `.claude/settings.local.json`. The builder picks whichever is reliable.
- **One switch.** The `wiki` key in `harness.json` turns on everything: the `wiki` skill, the Claude repo hook, the pi extension, and the generated `scripts/wiki.mjs`. Nobody has to list `"skills": ["wiki"]` as well. Listing the skill without the key is allowed (the skill alone, no hooks), so you can bootstrap a wiki before the config exists.
- **Opt-in pi extension.** Putting `wiki.ts` in `pi/extensions/` would load it in every repo, and narrowing with the spec's `extensions` field would switch off the other extensions. So it goes in a new `pi/extensions-opt-in/` directory, which the global `ai` package entry leaves out. `apply` adds a project-level package entry for it, tracked in state and removed when the `wiki` key goes. This follows the user's rule of per repo where possible.
- **Global fallback condition.** The fallback runs only when the repo has `docs/wiki/` and its `harness.json` has a `wiki` key. Having `docs/wiki/` alone isn't opting in, and the key is where the config comes from. Cloud sessions have `harness.json` because it's committed.
- **Skill in cloud.** As an opt-in skill, `wiki` never reaches cloud sessions, since those run only `install`. A `wiki` preset (`presets/wiki.json`) lets the cloud setup script add it with `--preset wiki`, the same way as `cloudflare`.
- **No wiki yet.** `apply` writes only `scripts/wiki.mjs`. In a repo without a wiki, an agent creates `docs/README.md` and `docs/wiki/` by following the skill's bootstrap steps. `apply` never creates or overwrites the project's conventions file.
- **Removing `wiki` from the spec.** This removes the hook, the pi entry, and the skill copy. `scripts/wiki.mjs` stays, so pre-commit keeps working, and `apply` warns that it's no longer updated and can be deleted along with its npm scripts.

## Constraints

- No dependencies. `wiki.mjs` stays a single Node file, as it is now.
- `apply` already writes `.claude/settings.local.json` through `claude plugin enable --scope local`. Adding the hook must merge into that file, never replace it, and removing `wiki` from the spec must remove only the hook it added.
- The global `ai` plugin is a `strict: false` marketplace entry generated by `air generate`. Never edit `.claude-plugin/marketplace.json` by hand.
- Run `node --test setup.test.mjs` after changing `setup.mjs`. Add tests for: the `wiki` spec field (valid, invalid, unknown keys), installing and removing the repo hook, the generated file and its ownership check, and the global hook's no-op paths.
- Update `README.md`'s spec field table and `harness.schema.json`.
- The repo is public: no credentials, and nothing from gym-rice that's private beyond the generic tooling.

## Left to the builder

- The exact `wiki` config shape beyond `sourceDirs`, based on what porting turns up.
- How the pi extension nudges at the end of a turn (`agent_settled` plus a follow-up message is the likely route; see `pi/extensions/turn-timeout.ts`).
- How the global plugin declares its hook (a `hooks` entry for the `ai` plugin in the generated marketplace, or `hooks/hooks.json` at the plugin root).
- Whether `apply` also prints the npm scripts a project should add (`wiki`, `wiki:check`, `wiki:affected`). Writing to `package.json` is out of scope.
